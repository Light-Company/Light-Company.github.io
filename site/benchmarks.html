Abstract

Controlled physical evaluation

A model comparison starts
with a comparable world.

Physical robot tests can change before a policy takes its first action. Object pose, clutter, lighting, and reset quality all affect the task. An aggregate score can hide these differences.

Prism's evaluation approach pairs a defined test condition with projected setup guidance and a vision check. Models are compared on matched cases, with completion criteria set in advance. Controlled sweeps then change one variable at a time to reveal the limits of each policy.

This preview demonstrates the intended reporting format: completion counts, task-level comparisons, and a capability map. The example data below illustrates how to read the report; it does not report a completed study.

  1. 01 / Define

    Specify the case.

    Record the task, objects, poses, conditions, model version, and completion rubric.

  2. 02 / Stage

    Project the setup.

    Guide placement on the work surface, then check the scene against its tolerances.

  3. 03 / Run

    Keep the comparison fair.

    Use matched cases, declared action budgets, and a reset between attempts.

  4. 04 / Score

    Keep the evidence.

    Separate setup rejection from task failure. Record outcomes, videos, and reasons.

  5. 05 / Map

    Change one condition.

    Sweep the variable of interest. Show tested regions, failures, and missing coverage.

How to read this preview +

All numbers and rankings are invented examples for the reporting design. Model names identify the example comparison lineup; they do not imply participation, endorsement, or a completed Prism evaluation. A publishable study must specify exact model checkpoints and settings, robot hardware, task definitions, budgets, reset checks, scoring rules, exclusions, and uncertainty. A capability map describes its sampled conditions, not every possible deployment.
